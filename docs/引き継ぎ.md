# 引き継ぎ資料 ― 応募候補リスト作成

本資料は `docs/architecture.md` §14 の骨子に基づき第1段階の引き継ぎとして
作成され、第2段階の実施結果までを追記している。設計の正本は
`docs/architecture.md`（旧追補統合済み）である。

## 配置表とサンプルの所在

- 配置表: `storage-spec/配置表.md`（モックアップ／サンプル一覧の正本）
- サンプル実体: `storage-spec/samples/`（検証用求人サンプル 39 件）
- 配置表を正とし、外部パスや一時 URL へのリンクのみで配置を済ませない。

## モックアップ／サンプルの更新手順

- 実体を差し替える場合は、配置表の「サイズ（バイト数）」「最終確認日」
  「サンプルの検証状態」を同時に更新し、配置表と実体の一致を読み戻して
  確認する（`tests/test_storage_spec.py` が一致を検証する）。
- 期待結果はサンプル実体には書かず、テスト側（`tests/`）にのみ保持する。

## ファイルの差し替え手順

- ファイル名は変えない。変える場合は配置表の ID を維持したまま、
  配置表の「ファイル名」列と「置き場のパス」列を更新する。
- ID（`SMP-001` 形式）は欠番・再利用をしない。

## 検証状態の見方

- `未検証`: まだ検証系に通していない状態。
- `検証済み（期待結果と一致）`: テストの期待結果と一致した状態。
- `検証済み（不一致あり）`: 不一致がある状態。理由を配置表の備考に残す。

## 設定ファイルの置き場

- テンプレート（伏せ字・git 管理）: `config/templates/`
  （`profile.example.yaml`／`judge.example.yaml`／`local.example.yaml`／
  `location_whitelist.example.yaml`）
- 実値（gitignore 対象・コミット禁止）: `config/local/`
  （`profile.local.yaml`／`judge.local.yaml`／`local.local.yaml`／
  `location_whitelist.local.yaml`）
- 禁止ワードリスト: リポジトリ直下の `banned_words.txt`（gitignore 対象）。
- 勤務地対応表の実値は確定値に更新済みである（ローカル設定のみ。
  「第2段階の実施結果」を参照）。市区町村名はローカル設定にのみ書き、
  テンプレート・コード・理由文には書かない。
- 情報源レジストリの正は、応募候補リスト Spreadsheet の「情報源レジストリ」
  タブである。実装側の設定ファイルにレジストリの判定値を置かない。
- ログイン必須の情報源候補（8 件）は、当初は全て「対象外（実測待ち）」で
  レジストリに記録した。第2段階でうち3件（求人サイト系）は実測成功済みとなり、
  残る確認は規約リスク評価等である。残りの情報源は実測（ブラウザでの
  ログイン確認）が先に必要である（architecture.md §8.5／§15、
  本資料「第2段階の実施結果」を参照）。

## 実行方法

前提: Python 3.11 以上。リポジトリ内に仮想環境を作り、依存を入れる。

```bash
python3 -m venv .venv
.venv/bin/pip install pytest PyYAML black isort
```

- テスト: `.venv/bin/python -m pytest`（全件 pass が実装完了の条件）
- 整形: `.venv/bin/python -m black src scripts`／
  `.venv/bin/python -m isort src scripts`
- push 前検閲: `.venv/bin/python scripts/pre_push_scan.py`
  （汎用パターンはスクリプト内、個人特定パターンは gitignore 対象の
  `scripts/pre_push_patterns.local.txt` から読む）
- CLI（手動実行。週次 cron は未作成）: `PYTHONPATH=src .venv/bin/python -m
  job_candidate_list.cli --config-dir config/local <サブコマンド>`
  - `validate-config`: 設定の検証のみ
  - `validate-registry`: レジストリの検証のみ
  - `dry-run`: ドライラン（シートへ書き込まない）
  - `collect`: 初回収集（本実行）
- 実 Sheets アクセスは `GoogleApiSheetsBackend` が
  `/opt/hatch/bin/hatch_gws_cli sheets ...` を呼び出す形で行う。

## 注意事項

- 自動応募フラグ（`auto_apply.enabled`）は既定 false。第1段階では常に
  false とし、変更は本人の明示指示によってのみ行う。
- OpenWork の点数付与は第1段階では行わない（レジストリのゲート無効が
  正常状態。全候補で OpenWork 関連 3 列は空欄）。
- 対外送信・応募・新規登録は行わない。取得は読み取りのみ・低頻度とする。

## 既知の課題（第1段階完了時点・QA検閲の申し送り）

- **M-1（第2段階の前提条件）**: `GoogleApiSheetsBackend` の CLI
  （`hatch_gws_cli`）経路は、書込（`write_rows` の `+append` 引数形式）と
  候補読取（`read_links` が CLI 経路では空を返し `read_candidates` が
  失敗する）の両方で実シートに対して機能しない。第2段階（週次更新の
  実装）に着手する前に、CLI の正規の引数形式（`--json-values` 等）へ
  修正し、実シートでの読み書き往復を検証すること。第1段階のシート
  実データはコネクタ経由の書込で作成・検証済みであり、影響はない。
  **解消済み（第2段階で解消）**: 書込はタブ（範囲）を指定できる正規形式
  `spreadsheets values append` に変更した（`--params` で
  spreadsheetId／range／valueInputOption=USER_ENTERED を指定し、
  `--json` で `{"values": [[...]]}` を渡す。複数行は1回の append に
  まとめる）。`+append` はタブ指定手段がなく先頭タブへ流れるため使わない。
  読取（リンク）は `spreadsheets values get` を
  valueRenderOption=FORMULA で呼び、`=HYPERLINK("url","text")` 数式から
  実 URL を (行, 列) 辞書に復元するようにした（数式内のエスケープ
  `""` → `"` にも対応）。Google API クライアント経路（service が
  渡された場合）の振る舞いは変更していない。文書化された CLI 形式に
  対するテスト（`tests/test_sheets_backend_cli.py` 4件）で往復・
  タブ独立性・複数行書込を確認済み。実シートでの読み書き往復も
  検証済み（2026-11-07、検証用一時タブで書込→読戻し照合→タブ削除を
  行い、本番タブの候補81行に影響がないことを確認。あわせて修正後の
  経路で実在候補81件の読み取りが全件成功することを確認）。
- **レジストリパーサの改行制約**: レジストリタブの構造化セル（実測
  結果・リスク評価結果と判定根拠）の中に改行を入れると、パース用
  正規表現が一致せず当該情報源が `SOURCE_BLOCKED` になる。構造化
  セルは1行で保持すること（自由記述の備考列は改行可）。
- **候補の質的課題（提示0件の根本原因）**: 初回リストは全件「要確認」
  となった。原因は判定ロジックではなく入力側にある（ATS の英語求人
  では日本語キーワードで主務を読み取りにくい、勤務地表記が広域で
  市区町村対応表と照合できない、構造化されたリモート頻度が無い）。
  改善の方向は、ログイン必須サイトの実測・対象化（国内の詳細な求人）
  と、個別企業の採用ページの情報源追加、英語キーワード設定の追加。
- **軽微な不統一**: 除外ログの一部で会社名がボード識別子のまま
  （m-1）、非正社員求人の一部が雇用形態でなく主務のルールIDで除外
  されている（m-2、結果は正しい）、Green 由来の候補で雇用形態が
  空欄のものがある（m-5）、英語スコア種別（TOEIC等）の識別正規表現
  がコード側にある（m-4）。

## 第2段階の実施結果（2026-11-07）

本人の判断（2026-11-07、組織リポジトリ Issue #1）を受けた実施結果。

- **勤務地対応表は確定値に更新済み**（ローカル設定のみ。東京都21区＝
  23区から世田谷区・大田区を除く、埼玉県6市、千葉県3市。境界5市区は
  対象外で確定）。
- **海外ATS系ソースは収集対象から除外**: ローカル設定の `ats_boards`
  を全て空にした（第1段階の設定値は `local.local.yaml.stage1.bak` に
  保全）。レジストリ側の判定値は変更していない。
- **試走（本番収集1回）**: 収集 0 件。国内の自動収集可ソースが実質
  存在しないため（Green は手動収集のみで自動実行対象外、その他の
  国内ソースはレジストリのフェイルクローズ条件で全て停止）。差分は
  棚上げ中の81件全件の掲載終了となり、大量変更ガードが停止したため
  シートへの書込は行われていない（81件は無傷）。
- **週次 cron は作成・有効化していない**（上記のとおり収集可ソースが
  実質ないため）。有効化の前提は次の2点。
  1. 国内ソースが最低1件、レジストリのゲート（実測成功・自動取得
     可否の確認・規約リスク評価・費用条件確認・最終判断）を通過する
     こと。候補: ビズリーチ／en-gage／paiza は実測成功済みで、残るは
     規約リスク評価と自動取得可否・費用条件の確認。doda／リクルート
     ダイレクトスカウト／Green ログイン側は実測（ブラウザでの
     ログイン確認）が先に必要。
  2. 棚上げ中の第1段階候補81件の扱いを決めること（現行のパイプ
     ラインは再取得されない既存候補を掲載終了として扱うため、この
     ままでは週次実行のたびに全件掲載終了の差分となり、ガードで
     停止し続ける）。
